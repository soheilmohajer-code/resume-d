گیت به زبان ساده: کنترل نسخه، گیت‌هاب و گیت‌لب بدون سردرگمی

گیت واقعاً چیست و چرا اول باید روی سیستم نصب شود، گیت‌هاب و گیت‌لب چه فرقی دارند (و چرا هر دو همان دستورات را می‌فهمند)، به‌علاوه گردش‌کار اصلی و چیت‌شیت.

English version of this post ❯

قبل از داکر و لینوکس، ابزاری که بیشترین تغییر روزانه در کارم ایجاد کرد گیت بود. هر پروژه‌ای که منتشر کرده‌ام — اپ‌های اندروید روی کافه‌بازار، افزونه‌ی ParsiChat Fixer، حتی همین وب‌سایت — داخل گیت زندگی می‌کند. و هر بار که دوستی از من خواسته برنامه‌نویسی یادش بدهم، دیده‌ام روی یک سردرگمی مشترک سکندری می‌خورد: قاطی‌کردن گیت با گیت‌هاب. این پست یک بار برای همیشه همه‌چیز را باز می‌کند.

خلاصه برای عجول‌ها — گیت ابزارِ کنترل نسخه است که باید روی کامپیوترت نصب شود (در ویندوز همراهش ترمینال Git Bash هم نصب می‌شود). گیت‌هاب و گیت‌لب وب‌سایت‌هایی هستند که مخازن گیت تو را آنلاین نگه می‌دارند. دستورات را یک بار یاد بگیر؛ هر دو پلتفرم همان زبان را حرف می‌زنند.

گیت واقعاً چیست؟

گیت یک سیستم کنترل نسخه‌ی توزیع‌شده است — ابزاری که از پروژه‌ات عکس‌های فوری (به نام کامیت) ثبت می‌کند تا به هر نقطه از تاریخ برگردی، روی خطوط زمانی موازی (به نام برنچ) آزمایش کنی، و کارِ چند نفر را بدون رونویسی شدن با هم ادغام کنی.

مثل سیستم ذخیره‌ی بازی‌های ویدیویی برای کد است:

  • سیو پوینت‌ها = کامیت‌ها. به‌هم ریخت؟ یک سیو عقب‌تر را لود کن.
  • نیو گیم پلاس = برنچ. ایده‌ی پرخطر را روی یک خط زمانی موازی امتحان کن بدون دست زدن به داستان اصلی.
  • چندنفره = merge. همه بازی می‌کنند و بعد خطوط زمانی با هم ترکیب می‌شوند.

دو ویژگی گیت را خاص می‌کند:

  1. توزیع‌شده — هر کسی که پروژه را clone کند کل تاریخ را روی سیستم خودش دارد. اینترنت نیست؟ می‌توانی کامیت کنی، برنچ بسازی و تاریخ را بگردی. سرور (گیت‌هاب/گیت‌لب) فقط جای همگام‌شدن تیم است — مغزِ ماجرا نیست.
  2. آدرس‌دهی محتوایی — هر عکس فوری هش SHA-1 یکتا می‌گیرد. اگر فایلی تغییر کند گیت می‌فهمد؛ هیچ‌چیز بی‌سروصدا گم نمی‌شود.
snippet.bash
$ git --version
git version 2.47.0.windows.1

اول: گیت باید روی سیستم نصب باشد

اینجاست که تازه‌کارها مدام گیر می‌کنند: گیت‌هاب یک وب‌سایت است، اما گیت برنامه‌ای است که روی کامپیوتر اجرا می‌شود — و آن وب‌سایت بدون گیتِ روی سیستمِ تو کار نمی‌کند.

نصب:

  • ویندوز — نصاب را از git-scm.com بگیر. این نصاب گیت و Git Bash را نصب می‌کند — ترمینالی که دستورات به سبک لینوکسی (ls، cd، ssh) می‌فهمد. به‌جای CMD یا PowerShell از Git Bash استفاده کن: همه‌ی آموزش‌های گیتِ دنیا این شل لینوکسی را فرض می‌کنند و ابزارهایی مثل ssh هم همراهش نصب‌اند.
  • لینوکس — یک دستور است: sudo apt install git (دبیان/اوبونتو).
  • مک — یک بار git --version را اجرا کن؛ مک پیشنهاد نصب می‌دهد.

اولین کاری که بعد از نصب باید بکنی — به گیت بگو کی هستی (روی هر کامیت مهر می‌خورد):

snippet.bash
git config --global user.name "Soheil Mohajer"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

با git --version و git config --list چک کن. حالا هر ابزاری — VS Code، Android Studio، ترمینال — می‌تواند روی آن سیستم از گیت استفاده کند.

گیت در برابر گیت‌هاب در برابر گیت‌لب

این جمله سردرگمی را تمام می‌کند:

گیت ابزار است؛ گیت‌هاب و گیت‌لب جاهایی هستند که مخازن گیت را هاست می‌کنند.

یک تشبیه: گیت دوربین است، گیت‌هاب و گیت‌لب اینستاگرام و گوگل‌فوتو. با دوربین عکس می‌گیری (گیت روی سیستم خودت)؛ روی پلتفرم آپلود و اشتراک می‌گذاری (ریموت). پلتفرم‌ها ابرقدرت‌هایی اضافه می‌کنند که دوربین ندارد: بکاپ، همکاری، بازبینی کد، پایپ‌لاین CI/CD، مدیریت ایشو.

گیت‌هاب گیت‌لب
مالکیت مایکروسافت (از ۲۰۱۸) GitLab Inc.
جایگاه بزرگ‌ترین — خانه‌ی متن‌باز پلتفرم کامل DevOps
CI/CD GitHub Actions (محصول جدا با پلن رایگان سخاوتمند) از روز اول داخلی، بسیار بالغ
نصب روی سرور خودی نه (Enterprise پولی است) بله، Community Edition رایگان — شرکت‌ها و حتی دولت‌ها نسخه‌ی خودشان را اجرا می‌کنند
مخازن خصوصی رایگان ✅ نامحدود ✅ نامحدود
هاست استاتیک GitHub Pages (همین سایت روش اجرا می‌شود!) GitLab Pages
بازبینی کد Pull Request Merge Request
اکوسیستم بزرگ‌ترین جامعه، بیشترین پروژه‌های عمومی قوی در دنیای سازمانی و self-host

نکته‌ی کلیدی: هر دو دقیقاً همان گیت را می‌فهمند. دستورات git push و git clone و git pull که یک بار یاد بگیری با هر دو یکسان کار می‌کنند. تفاوت در وب‌سایتی است که دورش ساخته شده: CI/CD داخلی و قابلیت self-host گیت‌لب آن را محبوب شرکت‌هایی کرده که همه‌چیز را یک‌جا و زیر سقف خودشان می‌خواهند؛ جامعه‌ی گیت‌هاب آن را پیش‌فرض متن‌باز کرده (و پروژه‌های عمومی من همان‌جاست).

یک مخزن حتی می‌تواند هم‌زمان به هر دو push کند — تیم‌ها معمولاً گیت‌هاب را روی گیت‌لب برای بکاپ mirror می‌کنند.

گردش‌کار اصلی (همان ۹۰٪ که هر روز استفاده می‌کنی)

فایل‌هایت در گیت سه «حوزه» دارند و هر دستور، فایل‌ها را بین‌شان جابه‌جا می‌کند:

snippet.txt
پوشه‌ی کاری  →(git add)→  محیط آماده‌سازی  →(git commit)→  مخزن محلی  →(git push)→  ریموت (گیت‌هاب/گیت‌لب)
snippet.bash
git clone https://github.com/user/repo.git   # یک نسخه از مخزن ریموت بگیر
cd repo

git status                # چه چیزی تغییر کرده؟ (همیشه بزن)
git add index.html        # یک فایل را آماده کن (یا: git add . همه)
git commit -m "Add hero section"   # از تغییرات آماده‌شده عکس فوری بگیر
git push                  # کامیت‌ها را به ریموت بفرست

git pull                  # کار بقیه را بگیر و ادغام کن
git log --oneline         # تاریخ را ورق بزن

مرتب کامیت کن، پیام واضح بنویس («Add hero section»، نه «آپدیت»)، و آخر هر جلسه‌ی کار push کن — همین عادت، بقیه‌ی مسیر را آسان می‌کند.

برنچ‌ها، و PR در برابر MR

برنچ یک خط زمانی موازی است. نسخه‌ی پیش‌فرض main است (در مخازن قدیمی master). برای ساختن یک قابلیت بدون خراب‌کردن نسخه‌ی سالم، برنچ می‌سازی:

snippet.bash
git switch -c feature/login    # برنچ جدید بساز و وارد شو
# ...کار کن، کامیت کن، تکرار...
git push -u origin feature/login

بعد — روی وب‌سایت — درخواست ادغام برنچت را باز می‌کنی:

  • گیت‌هاب اسمش را Pull Request (PR) گذاشته
  • گیت‌لب اسمش را Merge Request (MR) گذاشته

یک ایده، دو اسم: هم‌تیمی‌ها کد را بازبینی می‌کنند، CI تست‌ها را اجرا می‌کند و فقط بعد از آن به main می‌رسد. در تیم‌ها هیچ‌چیز مستقیم به main نمی‌رود — همه‌چیز از PR/MR می‌آید.

چیت‌شیت

snippet.bash
git init                          # گیت را در یک پوشه شروع کن
git clone <url>                   # کپی یک مخزن ریموت
git status                        # چه خبر؟ (همیشه!)
git add .                         # آماده‌سازی همه‌چیز
git commit -m "message"           # ثبت عکس فوری
git push / git pull               # همگام‌سازی با ریموت
git switch -c new-branch          # برنچ جدید
git merge feature/login           # آوردن یک برنچ
git log --oneline --graph         # تاریخ خوشگل
git restore file.txt              # لغو تغییرات کامیت‌نشده
git reset --soft HEAD~1           # لغو آخرین کامیت، حفظ تغییرات
git remote -v                     # لیست ریموت‌ها

چرا مهم است

کنترل نسخه تنها عادتی است که پروژه‌های تفننی را از حرفه‌ای‌ها جدا می‌کند. دکمه‌ی undo برای مسیر شغلی‌ات است، ماشین زمان برای کدهایت، و زبان مشترک هر تیم توسعه‌ی دنیا. گیت را نصب کن، Git Bash را باز کن، در یک پوشه‌ی تمرینی git init بزن — و امروز اولین کامیتت را بزن. پلتفرم‌ها هم همان‌جایند برای وقتی به آن‌ها نیاز داشته باشی.

نسخه‌ی ابزارها و امکانات پلتفرم‌ها سریع عوض می‌شود؛ جزئیات روز را از مستندات رسمی (git-scm.com، docs.github.com، docs.gitlab.com) چک کن.
