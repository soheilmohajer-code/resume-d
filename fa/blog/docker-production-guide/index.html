داکر برای توسعه‌دهنده‌ها: از کرنل تا پروداکشن

چرا داکر یاد گرفتم، کانتینر واقعاً چیست (به زبان ساده)، و یک مرجع پروداکشنی: ایمیلج‌ها و کش لایه‌ها، Docker Compose v2، شبکه و تله‌های امنیتی که هیچ‌کس درباره‌شان هشدار نمی‌دهد.

English version of this post ❯

مدت‌ها در برابر داکر مقاومت کردم. استدلالم همان استدلال کلاسیک هر توسعه‌دهنده بود: سیستم خودم همه‌چیز را درست اجرا می‌کند، چرا یک نهنگ به کارم اضافه کنم؟ دو پروژه نظر مرا عوض کرد.

اولی، self-host کردن n8n برای کارهای ایجنت‌هوش‌مصنوعی‌ام بود. راه رسمی و جدی اجرای n8n کانتینر است، و ظرف یک هفته آن ستاپ «موقت» تبدیل شد به یک compose.yaml که واقعاً به آن اعتماد دارم. دومی، دیپلوی پلتفرم دستیار هوش مصنوعی خودم (بک‌اند Next.js، PostgreSQL، Redis) روی یک VPS بود — جایی که فهمیدم جمله‌ی «روی سیستم خودم کار می‌کند» هیچ معنایی ندارد و داکر تنها پاسخ صادقانه به همان جمله است.

در این مسیر تقریباً همه‌ی تله‌های کلاسیک را خودم خوردم: پورت دیتابیسی که از داخل فایروال بی‌صدا به کل اینترنت باز شده بود، دیسکی که با لاگ و ایمیج‌های بی‌صاحب تا ۱۰۰٪ پر شد، و کانتینرهایی که نمی‌توانستند به دیتابیس «localhost» وصل شوند. این پست همان مرجعی است که آن هفته آرزو می‌کردم وجود داشت: اول داکر به زبان ساده، بعد بخش‌هایی که در پروداکشن واقعاً اهمیت دارند.

خلاصه برای عجول‌ها — کانتینر یک پروسه‌ی ایزوله است، نه یک ماشین مجازی کوچک. کش لایه‌ها را یاد بگیر، healthcheck کامپوز را یاد بگیر، و هرگز روی سرور عمومی به -p 8000:8000 اعتماد نکن. بقیه‌اش در همین پست است.

داکر به زبان ساده

شرکت‌های کشتیرانی دهه‌ها پیش این مشکل را حل کردند: به‌جای بارگیری کیسه و بشکه به‌تک‌تک روی کشتی‌های مختلف، کانتینر را استاندارد کردند — جعبه‌هایی که روی جرثقیل، کامیون و کشتی یکسان جا می‌گیرند. داخل جعبه چه باشد، برای هیچ‌کس که آن را جابه‌جا می‌کند مهم نیست.

داکر همین کار را با نرم‌افزار می‌کند. اپلیکیشن، ران‌تایم و وابستگی‌هایش را در یک کانتینر می‌گذاری و آن کانتینر روی لپ‌تاپ تو، سیستم هم‌تیمی‌ات و سرور Ubuntu یکسان اجرا می‌شود — چون محیط اجرا همراه اپ سفر می‌کند، نه همراه سیستم.

  • چیست؟ ابزاری که اپلیکیشن را همراه همه‌ی نیازهایش (ران‌تایم، کتابخانه‌ها، کانفیگ) در یک ایمیج بسته‌بندی می‌کند و آن ایمیج را به‌صورت کانتینر ایزوله اجرا می‌کند.
  • چه مشکلی را حل می‌کند؟ باگ‌های «روی سیستم من کار می‌کند»، تداخل وابستگی‌ها بین پروژه‌ها، دیپلوی دردناک و محیط‌هایی که با گذشت زمان از حالت استاندارد خارج می‌شوند.
  • کجاها استفاده می‌شود؟ self-host ابزارها (n8n، دیتابیس‌ها)، دیپلوی بک‌اندهای وب، پایپ‌لاین‌های CI/CD، محیط توسعه‌ی یکسان برای همه‌ی اعضای تیم، و اجرای میکروسرویس‌ها کنار هم روی یک سرور.

و یک جمله برای شکاک‌ها: کانتینر ماشین مجازی نیست — و دقیقاً از همین تمایز، درک واقعی شروع می‌شود.

زیر کاپوت: کانتینر فقط یک پروسه است

خیلی‌ها کانتینر را «ماشین مجازی سبک» تصور می‌کنند؛ از نظر فنی اشتباه است. کانتینر یک پروسه‌ی معمولی لینوکس است که دیدِ آن به سیستم محدود (ایزوله) شده و مصرف منابعش کنترل می‌شود.

ماشین مجازی (VM) کانتینر داکر
مجازی‌سازی سخت‌افزاری (Hypervisor: KVM، VMware، Hyper-V) سیستم‌عاملی (Docker Engine: containerd / runc)
کرنل هر VM سیستم‌عامل کامل با کرنل مجزا دارد همه‌ی کانتینرها کرنل مشترک هاست را استفاده می‌کنند
زمان بوت ده‌ها ثانیه تا چند دقیقه کسری از ثانیه (مثل اجرای یک پروسه‌ی عادی)
دیسک چند گیگابایت برای هر Guest OS چند مگابایت (لایه‌های پایه مشترک‌اند)
سربار قابل توجه تقریباً صفر (پرفورمنس Native)
ایزولاسیون بسیار قوی برای بیشتر کارها کافی (وقتی سخت‌سازی شود)

کل این ترفند روی سه قابلیتی بنا شده که سال‌هاست در کرنل لینوکس وجود دارد:

  1. Namespaces — دید پروسه را ایزوله می‌کند: PID جدا (pid)، کارت شبکه و پورت جدا (net)، نقاط مونت جدا (mnt)، هاست‌نیم (uts)، IPC (ipc) و نگاشت کاربر (user). داخل namespaceهای خودش، کانتینر صادقانه باور دارد تنها سیستم موجود در جهان است.
  2. cgroups (Control Groups) — مصرف پروسه را محدود می‌کند: CPU، رم، I/O. همان چیزی که mem_limit و سقف CPU واقعاً انجام می‌دهند.
  3. Union File System (لایه‌ها) — لایه‌های فقط-خواندنی ایمیج را روی هم می‌چیند و یک لایه‌ی نازک نوشتنی بالای آن می‌گذارد. به همین دلیل ایمیج‌ها کوچک و سریع pull می‌شوند و همین پایه‌ی کش لایه‌هاست که در ادامه از آن سوءاستفاده می‌کنیم.

ایمیلج‌ها، لایه‌ها و قانون طلایی کش

ایمیج در لایه‌ها ساخته می‌شود — هر دستور در Dockerfile (به‌ویژه FROM، RUN، COPY، ADD) یک لایه‌ی جدید با هش SHA256 یکتا می‌سازد.

قانون طلایی: داکر هنگام build لایه‌ها را از بالا به پایین بررسی می‌کند. به محض تغییر ورودی‌های یک لایه، آن لایه و همه‌ی لایه‌های بعدی باید از نو ساخته شوند. پس چیزهایی که به‌ندرت تغییر می‌کنند (نصب وابستگی‌ها) باید بالای چیزهایی که مدام تغییر می‌کنند (سورس کد) بیایند.

❌ ترتیب اشتباه — با هر تغییر کد، همه‌ی پکیج‌ها دوباره دانلود می‌شوند:

snippet.dockerfile
FROM python:3.12-slim
WORKDIR /app
# BAD: copying all source code first!
# Any change to main.py invalidates this layer AND the next RUN layer!
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
CMD ["python", "main.py"]

✅ ترتیب درست — وابستگی‌ها در کش می‌مانند، فقط کد rebuild می‌شود:

snippet.dockerfile
FROM python:3.12-slim
WORKDIR /app
# GOOD: copy ONLY dependency manifests first
COPY requirements.txt .
# Cached unless requirements.txt actually changes!
RUN pip install --no-cache-dir -r requirements.txt
# Now copy the frequently changing source code
COPY . .
CMD ["python", "main.py"]

مهم‌ترین دستورات، صادقانه توضیح داده‌شده:

دستور کار واقعی‌اش
FROM ایمیج پایه. نسخه‌های -slim (دبیان) یا -alpine (musl libc، خیلی کم‌حجم) را ترجیح بده.
WORKDIR دایرکتوری کاری را تعیین (و در صورت نبود می‌سازد). هرگز از RUN cd /app استفاده نکن.
COPY در برابر ADD همیشه COPY — شفاف است. ADD بی‌سروصدا .tar.gz را اکسترکت و URL دانلود می‌کند و رفتارهای غافلگیرکننده می‌آورد.
RUN در زمان build اجرا و نتیجه در لایه ثبت می‌شود. apt-get update && apt-get install -y ... را در یک RUN بنویس و آخرش کش apt را پاک کن.
ARG در برابر ENV ARG فقط زمان build وجود دارد (--build-arg)؛ ENV داخل کانتینر در حال اجرا هم می‌ماند.
EXPOSE صرفاً مستندسازی است. هیچ پورتی باز نمی‌کند — کار باز کردن پورت با -p است.

کانتینرها، چرخه‌ی حیات و دیباگ

چرخه‌ی حیات کانتینر همان چرخه‌ی پروسه است با چند state اضافه: created → running → paused → stopped → deleted. دستوراتی که روزانه استفاده می‌کنم:

snippet.bash
docker run -d --name api -p 127.0.0.1:8000:8000 app:1.0   # اجرا در پس‌زمینه
docker ps -a                                              # همه‌ی کانتینرها (حتی متوقف)
docker logs -f --tail 100 -t api                          # دنبال کردن ۱۰۰ خط آخر لاگ
docker exec -u 0 -it api /bin/sh                          # شل با دسترسی root داخل کانتینر
docker stats                                              # CPU/RAM زنده‌ی هر کانتینر
docker inspect api                                        # متادیتای کامل JSON
docker system df -v                                       # دیسکِ خورده‌شده توسط داکر

وقتی کانتینری فوراً خارج می‌شود، exit code را در docker ps -a چک کن: 137 معمولاً یعنی OOM-kill (تمام شدن رم) یا docker stop دستی، و 1 یعنی خود اپلیکیشن‌ات کرش کرده. خواندن exit code قبل از اجرای کورکورانه‌ی مجدد، ساعت‌ها وقت نجات می‌دهد.

داده‌ها: volumes، bind mount، tmpfs

کانتینرها یک‌بارمصرف‌اند؛ داده‌ی تو نباید باشد. سه راه ماندگاری:

  • Named volume (db-data:/var/lib/postgresql/data) — مدیریت‌شده توسط داکر؛ انتخاب پیش‌فرض درست برای فایل‌های دیتابیس.
  • Bind mount (./app:/app) — یک پوشه‌ی هاست را داخل کانتینر نگاشت می‌کند؛ ایده‌آل برای توسعه‌ی محلی و فایل‌های کانفیگ.
  • tmpfs — فقط در رم، با توقف از بین می‌رود؛ عالی برای /tmp در کانتینرهای سخت‌سازی‌شده‌ی پروداکشن.

هرگز داده را داخل ایمیج نجنبدان: لایه‌ی نوشتنی کند است و با کانتینر می‌میرد.

شبکه: DNS داخلی، ابرقدرت پنهان

هر پروژه‌ی کامپوز شبکه‌ی خودش را می‌سازد و روی آن شبکه اسم سرویس‌ها hostname است. بک‌اند تو به localhost:5432 وصل نمی‌شود — به db:5432 وصل می‌شود، چون روی شبکه‌ی کامپوز واقعاً هاستی به نام db وجود دارد. همین یک ایده، رایج‌ترین باگ تازه‌کارها (کانتینری که دنبال دیتابیس روی «localhost» خودش می‌گردد) را می‌کشد.

از دید هاست، ports: ["8000:8000"] روی همه‌ی اینترفیس‌ها publish می‌کند — این را برای بخش امنیت به خاطر بسپار.

Docker Compose v2، به شکل درست

کامپوز اجازه می‌دهد معماری چند-کانتینری را در یک compose.yaml اعلامی تعریف کنی. دو نکته‌ی مدرن: هدر منسوخ version: "3.8" در Compose Spec حذف شده، و docker-compose پایتونیِ قدیمی (با خط تیره) جای خود را به پلاگین Go یعنی docker compose (با فاصله) داده است.

نمونه‌ای با استانداردهای واقعی پروداکشن (FastAPI + PostgreSQL + Redis)، با healthcheck، شبکه‌های تفکیک‌شده و پورت بایند‌شده فقط به loopback:

snippet.yaml
name: my-saas-platform
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile
      target: runtime
    image: my-saas-backend:1.0.0
    restart: unless-stopped
    ports:
      # فقط روی localhost بایند شود تا UFW دور زده نشود!
      - "127.0.0.1:8000:8000"
    env_file: [.env]
    environment:
      - DATABASE_URL=postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      - REDIS_URL=redis://cache:6379/0
    # صبر کن تا Postgres و Redis واقعاً READY باشند
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    networks: [backend-net]
    develop:
      watch:
        - action: sync
          path: ./app
          target: /app/app
        - action: rebuild
          path: ./requirements.txt

  db:
    image: postgres:16.4-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-appuser}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Database password is required}
      POSTGRES_DB: ${POSTGRES_DB:-appdb}
    volumes:
      - pg_data:/var/lib/postgresql/data
    networks: [backend-net]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER:-appuser} -d $${POSTGRES_DB:-appdb}"]
      interval: 10s
      timeout: 5s
      retries: 5

  cache:
    image: redis:7-alpine
    restart: unless-stopped
    networks: [backend-net]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

volumes:
  pg_data:

networks:
  backend-net:
    driver: bridge

دو جزئیاتی که ارزش کپی‌کردن در فایل‌های خودت را دارند: depends_on با condition: service_healthy (اپ تو منتظر دیتابیسی می‌ماند که واقعاً آماده‌ی پذیرش اتصال است، نه صرفاً start شده) و develop.watch برای sync زنده هنگام توسعه.

امنیت پروداکشن: تله‌هایی که هیچ‌کس درباره‌شان حرف نمی‌زند

داکر روی لپ‌تاپ و داکر روی سرور عمومی زیر ترافیک واقعی، دو ورزش متفاوت‌اند. چهار چیزی که کاش کسی به من می‌گفت:

🚨 تله‌ی UFW — داکر فایروالت را دور می‌زند

ufw را فعال می‌کنی، فقط 22/80/443 را باز می‌گذاری، بعد دیتابیس را با -p 5432:5432 اجرا می‌کنی و خیال می‌کنی فایروال محافظتش می‌کند. نمی‌کند. داکر قوانین خودش را مستقیماً در زنجیره‌های PREROUTING/DOCKER در iptables می‌نویسد که قبل از قوانین UFW اجرا می‌شوند. پورت تو روی 0.0.0.0 باز است — برای کل اینترنت.

snippet.yaml
# DANGEROUS: exposes port 8000 to the world, bypasses UFW!
ports:
  - "8000:8000"
# SAFE: binds only to loopback (reachable by host Nginx, not the internet)
ports:
  - "127.0.0.1:8000:8000"

پورت‌های publish شده را به 127.0.0.1 بایند کن و بگذار reverse proxy روی هاست (Nginx/Caddy) با آن‌ها حرف بزند.

💾 چرخش لاگ، یا مرگ بی‌صدای دیسک

درایور لاگ پیش‌فرض json-file هیچ سقفی برای حجم ندارد. یک سرویس پرتکالم در چند هفته ده‌ها گیگابایت لاگ می‌نویسد و سرور را با دیسک ۱۰۰٪ زمین می‌زند. همیشه rotation را تنظیم کن:

snippet.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

🛡️ سقف منابع، فایل‌سیستم فقط-خواندنی و حذف capabilities

بدون سقف رم، یک کانتینر با memory leak کل سرور — حتی SSH — را با خودش می‌برد. در پروداکشن deploy.resources.limits را اضافه کن، با read_only: true و یک tmpfs روی /tmp اجرا کن (تا مهاجمی که وارد شد نتواند بدافزار روی دیسک ذخیره کند) و با cap_drop: [ALL] دسترسی‌های لازم نداشته‌ی کرنل را ببند.

🔑 Secrets جایگزین ENV است

متغیرهای محیطی را هر کسی که بتواند docker inspect اجرا کند می‌بیند و به پروسه‌های فرزند هم نشت می‌کنند. برای پسورد و کلید خصوصی از Docker secrets استفاده کن که به‌صورت فایل زیر /run/secrets/<name> (در رم، نه روی دیسک) mount می‌شوند:

snippet.yaml
services:
  db:
    secrets: [db_password]
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
secrets:
  db_password:
    file: ./secrets/db_password.txt

چیت‌شیت

snippet.bash
docker build -t app:1.0 .                       # بیلد با تگ
docker run -d --name api -p 127.0.0.1:8000:8000 app:1.0  # اجرا با پورت امن
docker logs -f --tail 100 -t api                # دنبال کردن لاگ
docker exec -u 0 -it api /bin/sh                # شل root داخل کانتینر
docker compose up -d --build                    # بیلد و اجرای کل استک
docker system df -v                             # تفکیک مصرف دیسک
docker run --rm -u $(id -u):$(id -g) -v $(pwd):/app -w /app python:3.12-slim pytest  # کانتینر یک‌بارمصرف تست
docker compose down -v --remove-orphans         # توقف و پاک‌سازی والیوم‌ها

داکر در نهایت چه چیزی به تو می‌دهد

از آن روز تا حالا، ارزش واقعی داکر برای من نه لوگوی نهنگ است و نه فایل‌های YAML. این است که استک خودکارسازی‌ام، پروژه‌های شخصی‌ام و سرورهایم حالا یک زبان مشترک دارند: همان ایمیجی که روی سیستمم build می‌شود، بدون تغییر روی VPS دیپلوی می‌شود، و وقتی چیزی می‌شکند، به‌جای دیباگ یک سرور برف‌گلوبی، لاگ یک پروسه را می‌خوانم. همین پیش‌بینی‌پذیری است که محصول واقعی است — بقیه‌ی این پست فقط راه رسیدن امن به آن بود.

این راهنما جمع‌بندی یادداشت‌های مطالعه‌ی من از مستندات رسمی داکر و تجربه‌های پروداکشن است؛ نسخه‌ها و فلگ‌ها سریع تغییر می‌کنند، پس همیشه با docs.docker.com چک کنید.
