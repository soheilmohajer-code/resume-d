25:T365c,<p>Every time I push to this website&#39;s repository, GitHub builds the site and
the domain updates itself — I don&#39;t copy a single file by hand. The first
time I saw that happen it felt like magic; then I learned it was CI/CD
quietly running under the floorboards of every serious software team. This
post is my study notes on that world — from why it existed in the first
place to exactly how it works.</p>
<blockquote>
<p><strong>TL;DR</strong> — CI/CD means continuously integrating code, then building,
testing and deploying software automatically. Errors surface the moment
they&#39;re born, releases shrink from months to minutes, and &quot;works on my
machine&quot; leaves the building.</p>
</blockquote>
<h2 id="why-it-came-to-exist">Why it came to exist</h2><p>In the old days at many organizations, developing and deploying software
belonged to two separate teams: <strong>Development</strong> and <strong>Operations</strong>.</p>
<p>Dev — the developers — wrote code, added features and fixed bugs. Ops owned
server provisioning, infrastructure, environment configuration, deployment,
and concerns like security and monitoring.</p>
<p>In traditional shops, when Dev finished a new version, they handed the
files over (say, a ZIP of the code) for Ops to deploy on the servers. And
it rarely went smoothly:</p>
<ul>
<li>The app might work on the developer&#39;s machine but fail on the server —
because of language version differences, libraries, environment settings,
or even the operating system.</li>
<li>Ops didn&#39;t know the internals of the code and couldn&#39;t easily tell where
the problem was; Dev didn&#39;t know enough about the server environment.
Finding and fixing errors took ages, and friction — and blame — grew
between the two teams.</li>
<li>The more changes piled up and the longer the gap between releases, the
harder merging and debugging became.</li>
</ul>
<p>(Nota bene: this wasn&#39;t a waterfall-only problem. Waterfall is the classic
sequential model — analysis, design, implementation, testing in order — but
the Dev/Ops wall can exist even in agile projects.)</p>
<p>To fix this, an approach called <strong>DevOps</strong> gradually emerged: shrink the
gap between development and operations so both deliver software faster and
more reliably, together. <strong>CI/CD is one of its most important tools</strong> — it
automates the repetitive work of building, testing and deploying, so errors
are caught earlier, releases get faster, and delivery becomes trustworthy.</p>
<p>And no — this doesn&#39;t make Ops obsolete. They still own infrastructure,
security, networking, monitoring and stability. The difference is that
automation makes much of the work standardized and fast.</p>
<h2 id="what-cicd-actually-is-and-how-it-works">What CI/CD actually is and how it works</h2><p>Picture several developers working on one project at once: one on user
login, another on payments. If each works in isolation for weeks and they
merge everything at the end, the code may be incompatible and the resulting
bugs can be nightmarish to locate.</p>
<p>CI/CD is a set of practices that keeps changes under <strong>continuous</strong>
verification, moving build, test, delivery and (when appropriate) deployment
forward with minimal manual intervention. Three core concepts:</p>
<h2 id="1-ci-continuous-integration">1) CI — Continuous Integration</h2><p>Developers push <strong>small changes frequently</strong> to a shared repository —
typically Git, hosted on GitHub, GitLab or Bitbucket.</p>
<p>(One small but real distinction: a repository is not the application&#39;s
database; it stores the project&#39;s files and their change history.)</p>
<p>The usual flow: the developer commits and pushes; the change goes through a
<strong>Pull Request</strong> (GitHub) or <strong>Merge Request</strong> (GitLab) for review; after
approval it merges into the main branch. And the moment that happens, an
automated process called a <strong>Pipeline</strong> runs: code checks, building the
app, running automated tests.</p>
<p>That&#39;s the magic of CI: if a change breaks an existing feature, the
automated tests expose it instantly — before it reaches the mainline or
production. So CI&#39;s goal isn&#39;t just &quot;merging code&quot;; it&#39;s <strong>frequent
integration and continuous verification</strong> so problems are found at the
earliest possible moment.</p>
<h2 id="2-pipelines-and-automated-testing">2) Pipelines and automated testing</h2><p>A <strong>Pipeline</strong> is a set of automated stages that run in a defined order. A
typical one:</p>
<ol>
<li><strong>Lint / code checks</strong> — surface-level errors, style issues, quickly
detectable problems.</li>
<li><strong>Build</strong> — code and dependencies are prepared into a usable output.</li>
<li><strong>Automated tests:</strong><ul>
<li><strong>Unit tests</strong> — does one small piece (say, a function) behave
correctly?</li>
<li><strong>Integration tests</strong> — do several parts of the app talk to each
other correctly?</li>
</ul>
</li>
</ol>
<p>The output of these stages may be an executable, a package, or a <strong>Docker
image</strong> — collectively called <strong>Artifacts</strong>.</p>
<p>Two honest notes:</p>
<ul>
<li><strong>A successful build ≠ a healthy app.</strong> It may build cleanly and still
break at runtime — which is exactly why tests belong in the pipeline.</li>
<li>The stages are executed by a <strong>Runner</strong> (GitLab&#39;s term) or <strong>Agent</strong>.
Each <strong>Job</strong> does one defined unit of work — e.g., &quot;run the tests&quot;. If a
required stage fails, the pipeline halts and reports the failure back to
the developer.</li>
</ul>
<p>And one engineering truth: automated testing doesn&#39;t guarantee zero bugs —
it guarantees that the errors you <em>wrote tests for</em> are found <strong>early</strong>.</p>

<h2 id="3-cd-continuous-delivery-and-continuous-deployment">3) CD — Continuous Delivery and Continuous Deployment</h2><p><strong>CD</strong> covers two related but distinct ideas:</p>
<ul>
<li><strong>Continuous Delivery:</strong> after passing review and tests, changes sit in
an &quot;always ready to release&quot; state — for example deployed to a
<strong>Staging</strong> environment (one that simulates production as closely as
possible). But the final release still needs a human approval.</li>
<li><strong>Continuous Deployment:</strong> if changes pass all automated tests and
criteria, they deploy to production <strong>automatically</strong> — no manual
sign-off per change.</li>
</ul>

<p>Automation doesn&#39;t remove tests or oversight — quite the opposite:
zero-touch deploys are only trustworthy with strong tests, security checks
and monitoring in place.</p>
<h2 id="a-real-example-the-online-shop">A real example: the online shop</h2><p>Say we run an online store and a developer wants to change the
discount-calculation logic:</p>
<ol>
<li><strong>Commit &amp; push</strong> — the change lands in GitLab.</li>
<li><strong>Pipeline fires</strong> — code checks run, the app builds.</li>
<li><strong>Automated tests</strong> — e.g., &quot;a 1,000,000-rial product with this discount
computes the right final price?&quot; and &quot;did the change break anything
that used to work?&quot;</li>
<li>If a test fails → pipeline fails → the developer fixes the problem
<strong>before release</strong>.</li>
<li>If everything passes → the built artifact deploys to <strong>Staging</strong> first.</li>
<li>Depending on whether the project uses Delivery or Deployment, production
goes out after an approval — or automatically.</li>
<li>After release, <strong>monitoring</strong> tools watch performance and errors; if the
new version misbehaves badly, a <strong>rollback</strong> restores the previous one.</li>
</ol>
<p>This example shows CI/CD isn&#39;t &quot;a few automated commands&quot; — it&#39;s a chain of
connected stages for reducing errors and increasing the speed and
confidence of delivery.</p>
