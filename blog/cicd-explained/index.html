CI/CD Explained: From Two Warring Teams to Zero-Touch Deploys

Why CI/CD was born, the real difference between Continuous Integration, Continuous Delivery and Continuous Deployment, how pipelines and automated tests work, what job statuses mean — with a real e-commerce example.

DATE: Oct 30, 2026READ: ~7 MINAUTHOR: SOHEIL MOHAJER

Every time I push to this website's repository, GitHub builds the site and the domain updates itself — I don't copy a single file by hand. The first time I saw that happen it felt like magic; then I learned it was CI/CD quietly running under the floorboards of every serious software team. This post is my study notes on that world — from why it existed in the first place to exactly how it works.

TL;DR — CI/CD means continuously integrating code, then building, testing and deploying software automatically. Errors surface the moment they're born, releases shrink from months to minutes, and "works on my machine" leaves the building.

Why it came to exist

In the old days at many organizations, developing and deploying software belonged to two separate teams: Development and Operations.

Dev — the developers — wrote code, added features and fixed bugs. Ops owned server provisioning, infrastructure, environment configuration, deployment, and concerns like security and monitoring.

In traditional shops, when Dev finished a new version, they handed the files over (say, a ZIP of the code) for Ops to deploy on the servers. And it rarely went smoothly:

  • The app might work on the developer's machine but fail on the server — because of language version differences, libraries, environment settings, or even the operating system.
  • Ops didn't know the internals of the code and couldn't easily tell where the problem was; Dev didn't know enough about the server environment. Finding and fixing errors took ages, and friction — and blame — grew between the two teams.
  • The more changes piled up and the longer the gap between releases, the harder merging and debugging became.

(Nota bene: this wasn't a waterfall-only problem. Waterfall is the classic sequential model — analysis, design, implementation, testing in order — but the Dev/Ops wall can exist even in agile projects.)

To fix this, an approach called DevOps gradually emerged: shrink the gap between development and operations so both deliver software faster and more reliably, together. CI/CD is one of its most important tools — it automates the repetitive work of building, testing and deploying, so errors are caught earlier, releases get faster, and delivery becomes trustworthy.

And no — this doesn't make Ops obsolete. They still own infrastructure, security, networking, monitoring and stability. The difference is that automation makes much of the work standardized and fast.

What CI/CD actually is and how it works

Picture several developers working on one project at once: one on user login, another on payments. If each works in isolation for weeks and they merge everything at the end, the code may be incompatible and the resulting bugs can be nightmarish to locate.

CI/CD is a set of practices that keeps changes under continuous verification, moving build, test, delivery and (when appropriate) deployment forward with minimal manual intervention. Three core concepts:

1) CI — Continuous Integration

Developers push small changes frequently to a shared repository — typically Git, hosted on GitHub, GitLab or Bitbucket.

(One small but real distinction: a repository is not the application's database; it stores the project's files and their change history.)

The usual flow: the developer commits and pushes; the change goes through a Pull Request (GitHub) or Merge Request (GitLab) for review; after approval it merges into the main branch. And the moment that happens, an automated process called a Pipeline runs: code checks, building the app, running automated tests.

That's the magic of CI: if a change breaks an existing feature, the automated tests expose it instantly — before it reaches the mainline or production. So CI's goal isn't just "merging code"; it's frequent integration and continuous verification so problems are found at the earliest possible moment.

2) Pipelines and automated testing

A Pipeline is a set of automated stages that run in a defined order. A typical one:

  1. Lint / code checks — surface-level errors, style issues, quickly detectable problems.
  2. Build — code and dependencies are prepared into a usable output.
  3. Automated tests:
    • Unit tests — does one small piece (say, a function) behave correctly?
    • Integration tests — do several parts of the app talk to each other correctly?

The output of these stages may be an executable, a package, or a Docker image — collectively called Artifacts.

Two honest notes:

  • A successful build ≠ a healthy app. It may build cleanly and still break at runtime — which is exactly why tests belong in the pipeline.
  • The stages are executed by a Runner (GitLab's term) or Agent. Each Job does one defined unit of work — e.g., "run the tests". If a required stage fails, the pipeline halts and reports the failure back to the developer.

And one engineering truth: automated testing doesn't guarantee zero bugs — it guarantees that the errors you wrote tests for are found early.

Job statuses

Status Meaning
Pending Ready to run, but no suitable runner is free yet
Running Currently executing — e.g., tests in flight
Success Finished successfully ✅
Failed Ended with an error — investigate ❌
Skipped Not run due to defined conditions or pipeline dependencies
Canceled Killed manually or by the process itself

If the test job shows Failed, one of its commands or tests broke. (These statuses describe Jobs; the pipeline's own status derives from its jobs and the defined structure.)

3) CD — Continuous Delivery and Continuous Deployment

CD covers two related but distinct ideas:

  • Continuous Delivery: after passing review and tests, changes sit in an "always ready to release" state — for example deployed to a Staging environment (one that simulates production as closely as possible). But the final release still needs a human approval.
  • Continuous Deployment: if changes pass all automated tests and criteria, they deploy to production automatically — no manual sign-off per change.
Continuous Delivery Continuous Deployment
Production release Manual approval Fully automatic
Always release-ready? Yes Yes
Fits Systems needing human control (e.g., banking) High-frequency web services

Automation doesn't remove tests or oversight — quite the opposite: zero-touch deploys are only trustworthy with strong tests, security checks and monitoring in place.

A real example: the online shop

Say we run an online store and a developer wants to change the discount-calculation logic:

  1. Commit & push — the change lands in GitLab.
  2. Pipeline fires — code checks run, the app builds.
  3. Automated tests — e.g., "a 1,000,000-rial product with this discount computes the right final price?" and "did the change break anything that used to work?"
  4. If a test fails → pipeline fails → the developer fixes the problem before release.
  5. If everything passes → the built artifact deploys to Staging first.
  6. Depending on whether the project uses Delivery or Deployment, production goes out after an approval — or automatically.
  7. After release, monitoring tools watch performance and errors; if the new version misbehaves badly, a rollback restores the previous one.

This example shows CI/CD isn't "a few automated commands" — it's a chain of connected stages for reducing errors and increasing the speed and confidence of delivery.

A real pipeline in the flesh (GitLab CI):

snippet.yaml
stages: [lint, build, test, deploy]

lint:
  stage: lint
  script: [ npm ci, npm run lint ]

build:
  stage: build
  script: [ npm run build ]
  artifacts:
    paths: [dist/]

test:
  stage: test
  script: [ npm test ]

deploy-staging:
  stage: deploy
  script: [ ./deploy.sh staging ]
  only: [ main ]

Is CI/CD the same everywhere?

No. A small project may need only a build and a few tests; a banking system adds security scans, access controls, release approvals, performance monitoring and advanced deployment strategies. Pipelines are shaped by each project's needs — but the goal is universal:

Ship changes to users faster, with higher quality, lower risk and more confidence.

CI/CD replaces scattered manual work with a process that is organized, repeatable, and as automatic as possible — which is exactly why it has become a backbone of modern software delivery.
