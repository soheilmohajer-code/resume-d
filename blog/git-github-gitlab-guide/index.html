Git Explained: Version Control, GitHub and GitLab Without the Confusion

What Git actually is and why it must be installed on your system first, how GitHub and GitLab differ (and why both use the same commands), plus the core workflow and a cheat sheet.

DATE: Oct 29, 2026READ: ~5 MINAUTHOR: SOHEIL MOHAJER

Before Docker, before Linux, the tool that changed how I work most daily was Git. Every project I've shipped — Android apps on Cafe Bazaar, the ParsiChat Fixer extension, even this website — lives in Git. And every time a friend asks me to teach them programming, I watch them trip over the same confusion: mixing up Git with GitHub. This post untangles it once and for all.

TL;DR — Git is the version-control tool that must be installed on your computer (on Windows it comes with the Git Bash terminal). GitHub and GitLab are websites that host your Git repositories online. Learn the commands once, and both platforms speak the same language.

What Git actually is

Git is a distributed version-control system — a tool that records snapshots of your project (called commits) so you can revisit any point in history, experiment on parallel timelines (called branches), and merge work from many people without overwriting each other.

Think of it like a video-game save system for code:

  • Save points = commits. Made a mess? Load an earlier save.
  • New game plus = branches. Try a risky idea on a side timeline without touching the main story.
  • Multiplayer = merging. Everyone plays, then the timelines combine.

Two properties make Git special:

  1. Distributed — everyone who clones a project has the full history on their machine. No internet? You can commit, branch and browse history offline. The server (GitHub/GitLab) is just where teams sync — not the brain.
  2. Content-addressed — every snapshot gets a unique SHA-1 hash. If a file changes, Git knows; nothing silently gets lost.
snippet.bash
$ git --version
git version 2.47.0.windows.1

First: Git must be on your system

This trips up beginners constantly: GitHub is a website, but Git is a program that runs on your computer — and the website can't work without it on your machine.

Installing:

  • Windows — download the installer from git-scm.com. It installs Git and Git Bash — a terminal that speaks Linux-style commands (ls, cd, ssh). Use Git Bash rather than CMD or PowerShell: every Git tutorial on Earth assumes this Linux-like shell, and tools like ssh come bundled.
  • Linux — it's one command: sudo apt install git (Debian/Ubuntu).
  • macOS — run git --version once; macOS offers to install it.

The first thing to do after installing — tell Git who you are (it stamps every commit with it):

snippet.bash
git config --global user.name "Soheil Mohajer"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

Verify with git --version and git config --list. Now every tool — VS Code, Android Studio, the terminal — can use Git on that machine.

Git vs GitHub vs GitLab

Here's the sentence that fixes the confusion:

Git is the tool; GitHub and GitLab are places that host Git repositories.

An analogy: Git is the camera, GitHub and GitLab are Instagram and Google Photos. You take photos with the camera (Git on your machine); you upload and share them on the platform (remote). The platforms add superpowers the camera doesn't have: backups, collaboration, code review, CI/CD pipelines, issue tracking.

Key insight: both speak exactly the same Git. The git push, git clone and git pull you learn once work identically with either. The differences are the website around it: GitLab's built-in CI/CD and self-hosting make it the favorite of companies that want everything in one place and under their own roof; GitHub's community makes it the default for open source (and it's where my public projects live).

One repo can even push to both at once — teams commonly mirror GitHub to GitLab for backup.

The core workflow (the 90% you'll use daily)

Git has three "areas" your files live in, and every command moves files between them:

snippet.txt
Working directory  →(git add)→  Staging area  →(git commit)→  Local repo  →(git push)→  Remote (GitHub/GitLab)
snippet.bash
git clone https://github.com/user/repo.git   # get a copy of a remote repo
cd repo

git status                # what changed? (use it constantly)
git add index.html        # stage one file (or: git add . for everything)
git commit -m "Add hero section"   # snapshot the staged changes
git push                  # upload commits to the remote

git pull                  # download + merge others' work
git log --oneline         # browse history

Commit often, write clear messages ("Add hero section", not "update"), and push at the end of a work session — that's the habit that makes everything else easy.

Branches, and PR vs MR

A branch is a parallel timeline. The default one is main (or master in older repos). You branch to build a feature without breaking the working version:

snippet.bash
git switch -c feature/login    # create + enter a new branch
# ...work, commit, repeat...
git push -u origin feature/login

Then — on the website — you open a request to merge your branch back:

  • GitHub calls it a Pull Request (PR)
  • GitLab calls it a Merge Request (MR)

Same idea, different name: teammates review the code, CI runs your tests, and only then does it land in main. In teams, nothing goes to main directly — everything arrives through PRs/MRs.

Cheat sheet

snippet.bash
git init                          # start Git in a folder
git clone <url>                   # copy a remote repo
git status                        # what's changed (always!)
git add .                         # stage everything
git commit -m "message"           # save a snapshot
git push / git pull               # sync with the remote
git switch -c new-branch          # new branch
git merge feature/login           # bring a branch in
git log --oneline --graph         # pretty history
git restore file.txt              # undo uncommitted changes
git reset --soft HEAD~1           # undo last commit, keep the changes
git remote -v                     # list remotes

Why it matters

Version control is the single habit that separates hobby projects from professional ones. It's the undo button for your career, the time machine for your code, and the shared language of every development team on Earth. Install Git, open Git Bash, type git init in a practice folder — and make your first commit today. The platforms will still be there when you need them.

Tool versions and platform features move fast; check the official docs (git-scm.com, docs.github.com, docs.gitlab.com) for current details.
