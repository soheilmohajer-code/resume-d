Docker for Developers: From Kernel to Production

Why I learned Docker, what containers actually are (in plain words), and a production-grade reference: images and layer caching, Compose v2, networking, and the security traps nobody warns you about.

DATE: Oct 29, 2026READ: ~8 MINAUTHOR: SOHEIL MOHAJER
$ docker compose up -dSTACK: RUNNING[OK]
نسخه‌ی فارسی این پست ❯

I resisted Docker longer than I should have. My thinking was the classic developer's: my machine runs everything fine, why add a whale to the mix? Two projects changed my mind.

The first was self-hosting n8n for my AI-agent work. The official way to run n8n seriously is a container, and within a week my "temporary" setup had become a compose.yaml I actually trust. The second was deploying my own AI-assistant platform (Next.js backend, PostgreSQL, Redis) to a VPS — where I learned that "it works on my machine" means nothing, and that Docker is the only honest answer to that sentence.

Along the way I hit every classic trap: a database port quietly exposed to the whole internet through my firewall, a disk filled to 100% by logs and dangling images, and containers that couldn't reach a database on "localhost". This post is the reference I wish I had that week: first Docker in plain words, then the parts of it that actually matter in production.

TL;DR — A container is an isolated process, not a small VM. Learn layer caching, learn Compose health checks, and never trust -p 8000:8000 on a public server. Everything else is in the sections below.

Docker in plain words

Shipping companies solved this problem decades ago: instead of loading sacks and barrels one by one onto different ships, they standardized containers — boxes that fit identically on a crane, a truck, or a ship. Whatever is inside doesn't matter to anyone handling the box.

Docker does the same for software. You put your app, its runtime, and its dependencies into a container, and it runs the same way on your laptop, your teammate's Windows machine, and a Ubuntu server — because the environment travels with the app, not the machine.

  • What it is: a tool that packages an application with everything it needs (runtime, libraries, config) into an image, and runs that image as an isolated container.
  • What problem it solves: "works on my machine" bugs, dependency conflicts between projects, painful deployments, and environments that drift over time.
  • Where it's used: self-hosting tools (n8n, databases), deploying web backends, CI/CD pipelines, giving every developer an identical dev environment, and running microservices side by side on one server.

And one sentence for the skeptical: a container is not a virtual machine — that distinction is where the real understanding starts.

Under the hood: containers are just processes

Many people imagine a container as a "lightweight VM". That's technically wrong. A container is an ordinary Linux process whose view of the system is limited (isolated) and whose resource usage is controlled.

Virtual Machine Docker Container
Virtualization Hardware-level (Hypervisor: KVM, VMware, Hyper-V) OS-level (Docker Engine: containerd / runc)
Kernel Each VM has a full guest OS with its own kernel All containers share the host Linux kernel
Boot time Tens of seconds to minutes Fraction of a second (a normal process start)
Disk Gigabytes per guest OS Megabytes (base layers are shared)
Overhead Notable Near zero (native performance)
Isolation Very strong Strong enough for most workloads (when hardened)

The whole trick rests on three features that have been in the Linux kernel for years:

  1. Namespaces — isolate what a process can see: its own process IDs (pid), network interfaces and ports (net), mount points (mnt), hostname (uts), IPC (ipc), and user mapping (user). Inside its namespaces, a container honestly believes it is alone in the world.
  2. cgroups (Control Groups) — limit what a process can use: CPU time, memory, I/O. This is what mem_limit and CPU caps actually do.
  3. Union file systems (layers) — stack read-only image layers and put a thin writable layer on top. This is what makes images small and fast to pull, and it's the foundation of the layer caching we exploit next.

Images, layers, and the golden rule of caching

An image is built in layers — each instruction in a Dockerfile (especially FROM, RUN, COPY, ADD) creates a new layer with a unique SHA256 hash.

The golden rule: Docker checks layers top-down during a build. The moment one layer's inputs change (cache invalidation), that layer and every layer after it must be rebuilt. So things that rarely change (installing dependencies) must come above things that change constantly (source code).

❌ Wrong order — every code edit re-downloads all packages:

snippet.dockerfile
FROM python:3.12-slim
WORKDIR /app
# BAD: copying all source code first!
# Any change to main.py invalidates this layer AND the next RUN layer!
COPY . .
RUN pip install --no-cache-dir -r requirements.txt
CMD ["python", "main.py"]

✅ Correct order — dependencies are cached, only code is rebuilt:

snippet.dockerfile
FROM python:3.12-slim
WORKDIR /app
# GOOD: copy ONLY dependency manifests first
COPY requirements.txt .
# Cached unless requirements.txt actually changes!
RUN pip install --no-cache-dir -r requirements.txt
# Now copy the frequently changing source code
COPY . .
CMD ["python", "main.py"]

The commands that matter most, honestly explained:

Command What it actually does
FROM Base image. Prefer -slim (Debian) or -alpine (musl libc, very small) variants.
WORKDIR Sets (and auto-creates) the working directory. Never use RUN cd /app.
COPY vs ADD Always prefer COPY — it's transparent. ADD silently extracts .tar.gz and fetches URLs, which invites surprising behavior.
RUN Executes at build time and bakes the result into a layer. Chain apt-get update && apt-get install -y ... in ONE RUN and clean the apt cache afterwards.
ARG vs ENV ARG exists only at build time (--build-arg); ENV persists into the running container.
EXPOSE Pure documentation between image author and runner. It opens no port — that's -p's job.

Containers, lifecycle, and debugging

A container's lifecycle is just a process's lifecycle with extra states: created → running → paused → stopped → deleted. The commands I use daily:

snippet.bash
docker run -d --name api -p 127.0.0.1:8000:8000 app:1.0   # run detached
docker ps -a                                              # all containers (incl. stopped)
docker logs -f --tail 100 -t api                          # follow last 100 log lines
docker exec -u 0 -it api /bin/sh                          # shell as root inside
docker stats                                              # live CPU/RAM per container
docker inspect api                                        # full JSON metadata
docker system df -v                                       # what's eating the disk

When a container exits immediately, check its exit code in docker ps -a: 137 usually means OOM-killed (out of memory) or a manual docker stop, while 1 is your application crashing on its own. Reading exit codes before re-running blindly saves hours.

Data: volumes, bind mounts, tmpfs

Containers are disposable; your data must not be. Three ways to persist:

  • Named volumes (db-data:/var/lib/postgresql/data) — Docker-managed, the right default for database files.
  • Bind mounts (./app:/app) — map a host folder in; ideal for local development and config files.
  • tmpfs — in-memory only, gone on stop; perfect for /tmp in hardened production containers.

Never bake data into an image: the writable layer is slow and dies with the container.

Networking: the internal DNS is the superpower

Every compose project creates its own network, and on that network service names are hostnames. Your backend doesn't connect to localhost:5432 — it connects to db:5432, because on the compose network there is a host called db. This one idea kills the most common beginner bug: a container trying to reach a database on "localhost" (which is the container itself).

From the host's perspective, ports: ["8000:8000"] publishes on all interfaces — remember this for the security section.

Docker Compose v2, done right

Compose lets you describe a multi-container architecture in one declarative compose.yaml. Two modernizations worth knowing: the obsolete version: "3.8" header is gone from the Compose Spec, and the old Python docker-compose (hyphen) is deprecated in favor of the Go plugin docker compose (space).

A production-shaped example (FastAPI + PostgreSQL + Redis), with health checks, separated networks, and a loopback-only port binding:

snippet.yaml
name: my-saas-platform
services:
  backend:
    build:
      context: .
      dockerfile: Dockerfile
      target: runtime
    image: my-saas-backend:1.0.0
    restart: unless-stopped
    ports:
      # Bind ONLY to localhost so UFW firewall isn't bypassed!
      - "127.0.0.1:8000:8000"
    env_file: [.env]
    environment:
      - DATABASE_URL=postgresql+asyncpg://${POSTGRES_USER}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB}
      - REDIS_URL=redis://cache:6379/0
    # Wait until Postgres and Redis are genuinely READY
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    networks: [backend-net]
    develop:
      watch:
        - action: sync
          path: ./app
          target: /app/app
        - action: rebuild
          path: ./requirements.txt

  db:
    image: postgres:16.4-alpine
    restart: unless-stopped
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-appuser}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?Database password is required}
      POSTGRES_DB: ${POSTGRES_DB:-appdb}
    volumes:
      - pg_data:/var/lib/postgresql/data
    networks: [backend-net]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER:-appuser} -d $${POSTGRES_DB:-appdb}"]
      interval: 10s
      timeout: 5s
      retries: 5

  cache:
    image: redis:7-alpine
    restart: unless-stopped
    networks: [backend-net]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5

volumes:
  pg_data:

networks:
  backend-net:
    driver: bridge

The two details worth copying into your own files: depends_on with condition: service_healthy (so your app waits for a database that is genuinely ready, not merely started) and develop.watch for live sync during development.

Production security: the traps nobody warns you about

Running Docker on a laptop and running it on a public server under real traffic are different sports. Four things I wish someone had told me:

🚨 The UFW trap — Docker bypasses your firewall

You enable ufw, allow only 22/80/443, then run a database with -p 5432:5432 believing the firewall protects it. It doesn't. Docker writes its own rules directly into the PREROUTING/DOCKER chains of iptables, which are evaluated before UFW's rules. Your port is open to 0.0.0.0 — to the entire internet.

snippet.yaml
# DANGEROUS: exposes port 8000 to the world, bypasses UFW!
ports:
  - "8000:8000"
# SAFE: binds only to loopback (reachable by host Nginx, not the internet)
ports:
  - "127.0.0.1:8000:8000"

Bind published ports to 127.0.0.1 and let a reverse proxy on the host (Nginx/Caddy) talk to them.

💾 Log rotation, or your disk dies quietly

The default json-file log driver has no size limit. A chatty service can write tens of gigabytes over a few weeks and take the whole server down at 100% disk. Always configure rotation:

snippet.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}

🛡️ Resource limits, read-only filesystems, and dropped capabilities

Without memory limits, one container with a memory leak takes the whole server — including SSH — down with it. In production, add deploy.resources.limits, run with read_only: true plus a tmpfs on /tmp (so an attacker who gets in can't persist malware), and drop kernel capabilities you don't need with cap_drop: [ALL].

🔑 Secrets are not ENV

Environment variables are readable by anyone who can run docker inspect, and they leak into child processes. For passwords and private keys use Docker secrets, mounted as files under /run/secrets/<name> (in RAM, not on disk):

snippet.yaml
services:
  db:
    secrets: [db_password]
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
secrets:
  db_password:
    file: ./secrets/db_password.txt

Cheat sheet

snippet.bash
docker build -t app:1.0 .                       # build with a tag
docker run -d --name api -p 127.0.0.1:8000:8000 app:1.0  # run, safe port
docker logs -f --tail 100 -t api                # follow logs
docker exec -u 0 -it api /bin/sh                # root shell inside
docker compose up -d --build                    # build & run the stack
docker system df -v                             # disk usage breakdown
docker run --rm -u $(id -u):$(id -g) -v $(pwd):/app -w /app python:3.12-slim pytest  # throwaway test container
docker compose down -v --remove-orphans         # stop & wipe volumes

What Docker actually buys you

Looking back, the value isn't the whale logo or the YAML. It's that my automation stack, my side projects, and my servers now share one vocabulary: the same image that builds on my machine deploys to the VPS unchanged, and when something breaks I debug a process with logs instead of a snowflake server. That predictability is the product — the rest of this post is just how to get it safely.

This guide reflects my study notes compiled from official Docker documentation and hard-won production lessons; versions and flags move fast, so always cross-check docs.docker.com.
