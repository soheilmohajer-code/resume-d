developer&#39;s: <em>my machine runs everything fine, why add a whale to the mix?</em>
Two projects changed my mind.</p>
<p>The first was self-hosting <strong>n8n</strong> for my AI-agent work. The official way to
run n8n seriously is a container, and within a week my &quot;temporary&quot; setup had
become a <code>compose.yaml</code> I actually trust. The second was deploying my own
AI-assistant platform (Next.js backend, PostgreSQL, Redis) to a VPS — where I
learned that &quot;it works on my machine&quot; means nothing, and that Docker is the
only honest answer to that sentence.</p>
<p>Along the way I hit every classic trap: a database port quietly exposed to the
whole internet <em>through</em> my firewall, a disk filled to 100% by logs and
dangling images, and containers that couldn&#39;t reach a database on &quot;localhost&quot;.
This post is the reference I wish I had that week: first Docker in plain
words, then the parts of it that actually matter in production.</p>
<blockquote>
<p><strong>TL;DR</strong> — A container is an isolated <em>process</em>, not a small VM. Learn

</blockquote>
<h2 id="docker-in-plain-words">Docker in plain words</h2><p>Shipping companies solved this problem decades ago: instead of loading
sacks and barrels one by one onto different ships, they standardized
<strong>containers</strong> — boxes that fit identically on a crane, a truck, or a ship.
Whatever is inside doesn&#39;t matter to anyone handling the box.</p>
<p>Docker does the same for software. You put your app, its runtime, and its
dependencies into a container, and it runs the same way on your laptop, your
teammate&#39;s Windows machine, and a Ubuntu server — because the <em>environment</em>
travels with the app, not the machine.</p>
<ul>
<li><strong>What it is:</strong> a tool that packages an application with everything it
needs (runtime, libraries, config) into an <strong>image</strong>, and runs that image
as an isolated <strong>container</strong>.</li>
<li><strong>What problem it solves:</strong> &quot;works on my machine&quot; bugs, dependency
conflicts between projects, painful deployments, and environments that
drift over time.</li>
<li><strong>Where it&#39;s used:</strong> self-hosting tools (n8n, databases), deploying web
backends, CI/CD pipelines, giving every developer an identical dev
environment, and running microservices side by side on one server.</li>
</ul>
<p>And one sentence for the skeptical: a container is <strong>not</strong> a virtual
machine — that distinction is where the real understanding starts.</p>
<h2 id="under-the-hood-containers-are-just-processes">Under the hood: containers are just processes</h2><p>Many people imagine a container as a &quot;lightweight VM&quot;. That&#39;s technically
wrong. A container is an ordinary Linux <strong>process</strong> whose <em>view</em> of the
system is limited (isolated) and whose resource usage is controlled.</p>

<p>The whole trick rests on three features that have been in the Linux kernel
for years:</p>
<ol>
<li><strong>Namespaces</strong> — isolate what a process can <em>see</em>: its own process IDs
(<code>pid</code>), network interfaces and ports (<code>net</code>), mount points (<code>mnt</code>),
hostname (<code>uts</code>), IPC (<code>ipc</code>), and user mapping (<code>user</code>). Inside its
namespaces, a container honestly believes it is alone in the world.</li>
<li><strong>cgroups (Control Groups)</strong> — limit what a process can <em>use</em>: CPU time,
memory, I/O. This is what <code>mem_limit</code> and CPU caps actually do.</li>
<li><strong>Union file systems (layers)</strong> — stack read-only image layers and put a
thin writable layer on top. This is what makes images small and fast to
pull, and it&#39;s the foundation of the layer caching we exploit next.</li>
</ol>
<h2 id="images-layers-and-the-golden-rule-of-caching">Images, layers, and the golden rule of caching</h2><p>An image is built in <strong>layers</strong> — each instruction in a <code>Dockerfile</code>
(especially <code>FROM</code>, <code>RUN</code>, <code>COPY</code>, <code>ADD</code>) creates a new layer with a unique
SHA256 hash.</p>
<p><strong>The golden rule:</strong> Docker checks layers top-down during a build. The
moment one layer&#39;s inputs change (cache invalidation), that layer <em>and every
layer after it</em> must be rebuilt. So things that rarely change (installing
dependencies) must come <strong>above</strong> things that change constantly (source
code).</p>
<p>❌ Wrong order — every code edit re-downloads all packages:</p>

<span class="line"><span>WORKDIR /app</span></span>
<span class="line"><span># BAD: copying all source code first!</span></span>

<code>created → running → paused → stopped → deleted</code>. The commands I use daily:</p>

exit codes before re-running blindly saves hours.</p>
<h2 id="data-volumes-bind-mounts-tmpfs">Data: volumes, bind mounts, tmpfs</h2><p>Containers are disposable; your data must not be. Three ways to persist:</p>
<ul>
<li><strong>Named volumes</strong> (<code>db-data:/var/lib/postgresql/data</code>) — Docker-managed,
the right default for database files.</li>
<li><strong>Bind mounts</strong> (<code>./app:/app</code>) — map a host folder in; ideal for local
development and config files.</li>
<li><strong>tmpfs</strong> — in-memory only, gone on stop; perfect for <code>/tmp</code> in hardened
production containers.</li>
</ul>
<p>Never bake data <em>into</em> an image: the writable layer is slow and dies with
the container.</p>
<h2 id="networking-the-internal-dns-is-the-superpower">Networking: the internal DNS is the superpower</h2><p>Every compose project creates its own network, and on that network
<strong>service names are hostnames</strong>. Your backend doesn&#39;t connect to
<code>localhost:5432</code> — it connects to <code>db:5432</code>, because on the compose network
there <em>is</em> a host called <code>db</code>. This one idea kills the most common beginner
bug: a container trying to reach a database on &quot;localhost&quot; (which is the
container itself).</p>
<p>From the host&#39;s perspective, <code>ports: [&quot;8000:8000&quot;]</code> publishes on all
interfaces — remember this for the security section.</p>

<code>compose.yaml</code>. Two modernizations worth knowing: the obsolete
<code>version: &quot;3.8&quot;</code> header is gone from the Compose Spec, and the old Python
<code>docker-compose</code> (hyphen) is deprecated in favor of the Go plugin
<code>docker compose</code> (space).</p>

<span class="line"><span style="color:#B8A965">  pg_data</span><span style="color:#666666">:</span></span>
<span class="line"></span>
<span class="line"><span style="color:#B8A965">networks</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#B8A965">  backend-net</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#B8A965">    driver</span><span style="color:#666666">:</span><span style="color:#C98A7D"> bridge</span></span></code></pre></div><p>The two details worth copying into your own files: <code>depends_on</code> with
<code>condition: service_healthy</code> (so your app waits for a database that is
<em>genuinely ready</em>, not merely started) and <code>develop.watch</code> for live sync
during development.</p>
<h2 id="production-security-the-traps-nobody-warns-you-about">Production security: the traps nobody warns you about</h2><p>Running Docker on a laptop and running it on a public server under real
traffic are different sports. Four things I wish someone had told me:</p>
<h3 id="the-ufw-trap-docker-bypasses-your-firewall">🚨 The UFW trap — Docker bypasses your firewall</h3><p>You enable <code>ufw</code>, allow only 22/80/443, then run a database with
<code>-p 5432:5432</code> believing the firewall protects it. <strong>It doesn&#39;t.</strong> Docker
writes its own rules directly into the <code>PREROUTING</code>/<code>DOCKER</code> chains of
iptables, which are evaluated <em>before</em> UFW&#39;s rules. Your port is open to
<code>0.0.0.0</code> — to the entire internet.</p>
<div class="term" dir="ltr"><div class="term-bar"><span class="d d1"></span><span class="d d2"></span><span class="d d3"></span><span class="file">snippet.yaml</span><button type="button" class="copy" data-copy>COPY</button></div><pre class="shiki vitesse-dark" style="background-color:#121212;color:#dbd7caee" tabindex="0"><code><span class="line"><span style="color:#758575DD"># DANGEROUS: exposes port 8000 to the world, bypasses UFW!</span></span>
<span class="line"><span style="color:#B8A965">ports</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#666666">  -</span><span style="color:#C98A7D77"> "</span><span style="color:#C98A7D">8000:8000</span><span style="color:#C98A7D77">"</span></span>
<span class="line"><span style="color:#758575DD"># SAFE: binds only to loopback (reachable by host Nginx, not the internet)</span></span>
<span class="line"><span style="color:#B8A965">ports</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#666666">  -</span><span style="color:#C98A7D77"> "</span><span style="color:#C98A7D">127.0.0.1:8000:8000</span><span style="color:#C98A7D77">"</span></span></code></pre></div><p>Bind published ports to <code>127.0.0.1</code> and let a reverse proxy on the host
(Nginx/Caddy) talk to them.</p>
<h3 id="log-rotation-or-your-disk-dies-quietly">💾 Log rotation, or your disk dies quietly</h3><p>The default <code>json-file</code> log driver has <strong>no size limit</strong>. A chatty service
can write tens of gigabytes over a few weeks and take the whole server down
at 100% disk. Always configure rotation:</p>
<div class="term" dir="ltr"><div class="term-bar"><span class="d d1"></span><span class="d d2"></span><span class="d d3"></span><span class="file">snippet.json</span><button type="button" class="copy" data-copy>COPY</button></div><pre class="shiki vitesse-dark" style="background-color:#121212;color:#dbd7caee" tabindex="0"><code><span class="line"><span style="color:#666666">{</span></span>
<span class="line"><span style="color:#B8A96577">  "</span><span style="color:#B8A965">log-driver</span><span style="color:#B8A96577">"</span><span style="color:#666666">:</span><span style="color:#C98A7D77"> "</span><span style="color:#C98A7D">json-file</span><span style="color:#C98A7D77">"</span><span style="color:#666666">,</span></span>
<span class="line"><span style="color:#B8A96577">  "</span><span style="color:#B8A965">log-opts</span><span style="color:#B8A96577">"</span><span style="color:#666666">:</span><span style="color:#666666"> {</span><span style="color:#B8A96577"> "</span><span style="color:#B8A965">max-size</span><span style="color:#B8A96577">"</span><span style="color:#666666">:</span><span style="color:#C98A7D77"> "</span><span style="color:#C98A7D">10m</span><span style="color:#C98A7D77">"</span><span style="color:#666666">,</span><span style="color:#B8A96577"> "</span><span style="color:#B8A965">max-file</span><span style="color:#B8A96577">"</span><span style="color:#666666">:</span><span style="color:#C98A7D77"> "</span><span style="color:#C98A7D">3</span><span style="color:#C98A7D77">"</span><span style="color:#666666"> }</span></span>
<span class="line"><span style="color:#666666">}</span></span></code></pre></div><h3 id="resource-limits-read-only-filesystems-and-dropped-capabilities">🛡️ Resource limits, read-only filesystems, and dropped capabilities</h3><p>Without memory limits, one container with a memory leak takes the whole
server — including SSH — down with it. In production, add
<code>deploy.resources.limits</code>, run with <code>read_only: true</code> plus a <code>tmpfs</code> on
<code>/tmp</code> (so an attacker who gets in can&#39;t persist malware), and drop kernel
capabilities you don&#39;t need with <code>cap_drop: [ALL]</code>.</p>
<h3 id="secrets-are-not-env">🔑 Secrets are not ENV</h3><p>Environment variables are readable by anyone who can run <code>docker inspect</code>,
and they leak into child processes. For passwords and private keys use
Docker <strong>secrets</strong>, mounted as files under <code>/run/secrets/&lt;name&gt;</code> (in RAM,
not on disk):</p>
<div class="term" dir="ltr"><div class="term-bar"><span class="d d1"></span><span class="d d2"></span><span class="d d3"></span><span class="file">snippet.yaml</span><button type="button" class="copy" data-copy>COPY</button></div><pre class="shiki vitesse-dark" style="background-color:#121212;color:#dbd7caee" tabindex="0"><code><span class="line"><span style="color:#B8A965">services</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#B8A965">  db</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#B8A965">    secrets</span><span style="color:#666666">:</span><span style="color:#666666"> [</span><span style="color:#C98A7D">db_password</span><span style="color:#666666">]</span></span>
<span class="line"><span style="color:#B8A965">    environment</span><span style="color:#666666">:</span></span>
<span class="line"><span style="color:#B8A965">      POSTGRES_PASSWORD_FILE</span><span style="color:#666666">:</span><span style="color:#C98A7D"> /run/secrets/db_password</span></span>

It&#39;s that my
